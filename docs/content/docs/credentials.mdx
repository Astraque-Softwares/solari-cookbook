title: Provider credentials
description: Configure Groq and Solari securely for local runs, CI, and one-run terminal use.
---

FlakeLab's local scan, analysis, discovery, replay, and offline reporting do not need provider
credentials. The complete investigation-and-proof journey needs **both** keys:

| Variable | Used for |
| --- | --- |
| `GROQ_API_KEY` | AI investigation and candidate generation. |
| `SOLARI_API_KEY` | Disposable isolated proof and optional report publication. |

FlakeLab connects directly to Groq and Solari. It has no credential relay. The keys are read only
when a provider-backed phase is approved, are never written to evidence, are removed from the
environment passed to Playwright, and are not copied into a proof sandbox.

## Option 1: hidden prompts for one run

This is the safest convenient option on a developer machine. Start the normal interactive flow:

```bash
npx flakelab@latest diagnose "tests/checkout.spec.ts:42"
```

Approve the Solari proof and Groq candidate prompts. If either key is missing, FlakeLab requests it
through hidden terminal input. The value remains only in memory until that FlakeLab process exits.

Use `--prompt-credentials` to ignore values already present in the environment or `.env` file and
enter both replacements for that run:

```bash
npx flakelab@latest diagnose "tests/checkout.spec.ts:42" --repair --prompt-credentials
```

Hidden prompts require an interactive terminal. CI and redirected input fail instead of hanging.

## Option 2: current terminal session

Environment variables are useful when several commands in one trusted terminal need the same
credentials. Avoid putting literal keys in commands, because shell history can retain them.

### PowerShell 7

```powershell
$env:GROQ_API_KEY = Read-Host "GROQ_API_KEY" -MaskInput
$env:SOLARI_API_KEY = Read-Host "SOLARI_API_KEY" -MaskInput
npx flakelab@latest diagnose "tests/checkout.spec.ts:42" --repair
Remove-Item Env:GROQ_API_KEY, Env:SOLARI_API_KEY
```

The variables belong to that PowerShell process and its children; they disappear when the shell
closes. The final command removes them earlier.

### Bash or zsh

```bash
read -rsp "GROQ_API_KEY: " GROQ_API_KEY && export GROQ_API_KEY && printf '\n'
read -rsp "SOLARI_API_KEY: " SOLARI_API_KEY && export SOLARI_API_KEY && printf '\n'
npx flakelab@latest diagnose "tests/checkout.spec.ts:42" --repair
unset GROQ_API_KEY SOLARI_API_KEY
```

## Option 3: a project `.env` file

Create `.env` in the directory from which you run FlakeLab:

```dotenv
GROQ_API_KEY=replace_with_your_groq_key
SOLARI_API_KEY=replace_with_your_solari_key
```

FlakeLab loads this file automatically after checking the current process environment. A process
variable therefore wins over the same name in `.env`.

Before creating the file, ensure the repository ignores it:

```text
.env
.env.*
!.env.example
.flakelab/
```

An `.env` file is plaintext. Use it only on a trusted machine, restrict file access, never commit
it, and put placeholders - not working credentials - in `.env.example`. FlakeLab does not search
arbitrary parent folders for secrets; this keeps repository boundaries explicit.

## Option 4: CI secret storage

Store both values in the CI provider's encrypted secret store and expose them only to the
provider-backed job. For GitHub Actions, use a protected environment such as `flakelab`:

```yaml
jobs:
  proof:
    environment: flakelab
    env:
      GROQ_API_KEY: ${{ secrets.GROQ_API_KEY }}
      SOLARI_API_KEY: ${{ secrets.SOLARI_API_KEY }}
```

Require environment reviewers, do not expose secrets to fork pull requests, do not use
`pull_request_target` to run untrusted code, and avoid commands that print the environment.

## Lookup order

FlakeLab checks credentials in this order:

1. current process environment;
2. `.env` in the current working directory;
3. hidden interactive prompt.

`--prompt-credentials` deliberately skips the first two sources. There is no `--api-key` option:
command arguments can leak through process listings, logs, and shell history.

## Security checklist

- Create separate, least-privilege, low-balance keys for local development and CI.
- Keep keys out of source files, test fixtures, Playwright configuration, issue reports, traces,
  screenshots, and `.flakelab` artifacts.
- Never paste a key into a command argument, chat, build log, or committed configuration file.
- Restrict CI secrets to protected branches and reviewed environments.
- Treat signed Solari session or file URLs as secrets too.
- Rotate a key immediately if it may have been exposed. Solari documents that a key is displayed
  only once and can authorize billable resources and account data.
- Verify cleanup in the proof report: created and released resource counts must match and
  remaining live resources must be zero.

See the [Solari quickstart](https://docs.getsolari.com/quickstart) for creating and rotating a
Solari key, and [AI and security](/docs/ai-and-security) for FlakeLab's broader trust boundary.
